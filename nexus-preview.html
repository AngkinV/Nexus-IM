02
Architecture

三个进程，一条单向闭环

系统被刻意切成三段：Java 网关、Python Agent、客户端。 流量只能沿着一个方向流 —— 客户端永远只跟 Java 说话，Java 永远不直接调 LLM， Python 也永远不直接面对客户端。这条约束是后面所有设计的地基。

REST / STOMP 内部 HMAC 调用 持久化
01

客户端只认一个入口

桌面端和网页端共用同一份前端产物，所有请求打 Java 网关。鉴权、限流、清洗、校验都在这一层收口。

02

Java 是唯一数据源

用户、会话、消息、群组、好友、文件、同步 —— 只有 Java 能写库。Agent 想要数据，必须反过来问它。

03

Python 只负责推理

它不持业务数据、不存用户密钥、不对外开端口。拿到的是递过来的上下文和一次性的模型凭据。

03
Realtime

一条频道，承载所有实时事件

大多数 IM 的做法是「每个会话一个 topic」。Nexus 反过来：所有事件都往 /topic/user.{id}.messages 这一个频道投。少了一层订阅管理， 也让「换设备」「多端在线」不需要重新协商订阅。

Channel
/topic/user.{id}.messages 承载新消息、ACK、输入中、已读回执、群成员变化、通话信令、错误事件。一条连接，一个订阅，全量事件。
Presence
在线状态不落数据库，改用 Redis 90 秒 TTL + 客户端 30 秒心跳。进程崩了状态自己会过期，不会留下「永远在线」的僵尸用户。
Offline
目标离线时消息先进 Redis 队列，用户上线后按序回放 —— 不丢，也不靠客户端轮询补。
Ordering
单调递增的 sequenceNumber 由 Redis INCR 生成，多实例并发下顺序也不会乱。
Scale-out
跨实例靠 Redis Pub/Sub 广播，各实例自己判断目标用户是否挂在本地连接上 —— 加机器不用改协议。
Security
握手必须带 JWT，已吊销的会话连不进来，也只能订阅自己的频道。连接不再接受「报个 userId 就放行」。
Offline-first
前端先渲染再等服务端确认：临时消息 → ACK 后合并成正式消息 → 失败则标红可重发。断网期间进本地待发队列，重连后冲出去。
04
Design
Decisions

需要做决定，才做得出来的东西

下面这些不是功能清单，而是设计上真正要取舍的地方。

01

工具定义在 Java，Python 只负责发现

Python 里一个工具都没写。Java 用 MCP 协议暴露工具，Agent 启动时发现后原样交给模型。

加一个工具不用改 Python，也不用重新部署 Agent 服务。

为什么重要 工具需要读业务数据，而业务数据只有 Java 有。把工具留在数据旁边，Agent 就永远不会拿着过期的接口干活。
MCP7 个只读工具零 Python 改动
02

密钥进 Java，不进 Agent

用户在网关录入 provider 和 key，Java 加密落库。调 Agent 时通过请求头一次性转发。

Python 进程里没有用户密钥的副本。

为什么重要 Agent 是最容易被拿去加日志、开 debug 的那个服务。让它天然不含密钥，等于把泄露面砍掉一半。
BYOK加密落库
03

一轮推理被打断，可以从断点续跑

编排只有一套图：准备上下文 → 推理 ⇄ 调工具 → 校验输出。每一步落 checkpoint。

模型报错、断线、进程被杀，从最后完成的一步继续。

为什么重要 一轮可能跑几十秒、调好几次工具。没有 checkpoint，用户按一次重试就是全额重算。
LangGraph可续跑

05

离线优先，不是「断网即废」

前端有一整套本地库：消息、会话、联系人、同步元信息、待发队列。

启动顺序：先开界面 → 连长连接 → 拉增量 → 冲离线队列。重连后靠增量同步对齐，不是全量重拉。

为什么重要 桌面端会长时间挂着、会睡眠、会切网。薄前端在这种场景下体验会碎得很明显。
IndexedDB增量同步待发队列
06

角色会眨眼、呼吸、视线游移

3D 形象不只是静态模型。有一层程序化「生命感」：眨眼间隔随机、偶尔连眨两下、呼吸频率带噪声漂移、视线缓慢游移。

支持多种模型格式，动作库可配置，尊重系统「减少动态效果」设置。

为什么重要 完全静止的模型会让人立刻意识到「这是个贴图」。真正让人觉得「在」的，是这些几像素级的小动作。
three-vrm程序化呼吸reduced-motion
05
Agent

Agent 拿到的是真实会话

这是 Nexus 和「聊天框旁边挂个 AI」最本质的区别： 模型读的上下文来自数据库里的真实消息，它调的工具直接查聊天记录， 回答里引用的来源可以点开核对。

Context

工具读的是真消息

七个只读工具：最近消息、会话资料、用户资料、单条消息、按用户名找人、我的会话列表、与某人的私聊。

特定任务强制要求至少调一次「最近消息」—— 从机制上堵住幻觉。

Knowledge

知识库是模块化的

文档入库：加载 → 切片 → 向量化 → 写向量库。检索取最相关的几条。

支持 PDF / DOCX / TXT / MD。入库失败会把状态写回业务侧，用户在界面上看得到是哪一步断了。

Providers

多类客户端，一套接口

OpenAI 兼容 / Anthropic / Gemini 各有一套适配，外加工厂统一选择。Embedding 侧有六个预设。

没配 key 的时候不是崩，而是走确定性回复，让链路仍然可测。

Honesty

不知道就说不知道

知识库检索永远返回成功，空结果交给业务侧渲染「我不知道」，而不是伪造一段看起来像答案的东西。

回答带来源列表，每条能点开看到原文摘录。
