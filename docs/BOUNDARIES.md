## 2. 项目定位（不可漂移）

带 AI 助手的即时通讯。

- **Java 后端是唯一业务数据源**（用户/鉴权、消息、群组、联系人、文件、同步、WebSocket、Agent 网关、知识库编排、Companion）。
- **Python Agent 只在内网**，不直接面对客户端；由 Java 经 HMAC 调用，Agent 经 Bearer 反向回调 Java 内部接口。
- **Web 与 Electron 是唯一客户端**。

任何把「唯一数据源」变成多源、把 Agent 暴露到公网、或新增客户端平台的做法，都属于越界，须先改本文。

## 3. 范围边界

### 3.1 模块处理方式（以 ROADMAP 为准）

| 处理 | 模块 | 边界 |
|---|---|---|
| **保留并投入** | 聊天核心、用户鉴权、Agent、知识库 | 主链路持续打磨，缺口见 GAPS |
| **合并** | Companion 并入 Agent，作为一个人设 | 方向已定；合并前不允许再往 Java 直连 LLM 管线加新功能（见 §4.1） |
| **保留但默认关** | 3D 形象 | 用户打开后才加载资源；默认态不得强制下载 Three.js/模型 |
| **冻结（保留代码，不再投入）** | 社区帖子、LangGraph 备选引擎、音视频通话 | 不删代码，但**不加新功能、不修非阻断性 bug**；通话 UI 入口按 FE-10 收敛 |
| **停止** | 手机端 `nexus-chat-app` | 全部开发停止；源码已移出 git，仅本机残留目录，禁止误提交 |

### 3.2 不做的方向

- **不换 Rust 重写后端**。
- 客户端内存先做按需加载，**实测后**再评估 Electron 换 Tauri，禁止凭感觉提前换。

### 3.3 历史冲突裁决

| 冲突 | 裁决 |
|---|---|
| `DEVELOPMENT.md` 说「`main` 是正本」；`GIT-CHECKLIST.md` 说「`feature-branch` 是主线」 | **以 GIT-CHECKLIST 为准**：`feature-branch` 是主线（GitHub 默认分支），所有 PR 合到这里；`main` 是**稳定兜底分支**，`feature-branch` 稳定后才同步过去，不直接从 `main` 开发或合并 |

## 4. 架构红线

1. **Java 永不直连 LLM。** 所有模型调用统一走 Python Agent。Companion 是这一红线的已知例外（`CompanionModelService` 直连），但它是待合并项——**禁止再往这条管线加新能力**，新模型需求一律走 Agent。
2. **只有一套模型凭据/Provider 体系**（合并方向）。当前 Companion 与 Agent 各自一套是待收敛状态，新增凭据能力不得再开出第三套。
3. **Agent 只对内网。** 内部互信走 HMAC 签名 + Bearer 回调令牌；不新增对客户端的直连通道。
4. **前端不新开数据源。** 前端缓存（IndexedDB）是 Java 数据的缓存副本，不是真相源；一切状态以 Java 返回为准。
5. **写操作要确认。** Agent 侧任何写操作（发消息、建群等）必须先经用户逐次确认（ROADMAP M4）；未确认不落库。

## 5. 数据与安全红线

1. **密钥不进仓库。** 仓库只放 `.env.example`（占位符）；真实值在本机 `.env`（已被 gitignore）。禁止把任何密钥、口令、令牌的值写进文档、代码注释或提交信息。
2. **运行数据不进仓库。** 用户上传文件（`uploads/`）、向量库（`nexus-agent-backend/data/`）、MySQL 数据等只留在本机，均已 gitignore。
3. **凭据布局固定**（详见 GIT-CHECKLIST §3）：
   - `application-local.properties`、`agent-backend/.env` 为本地真实凭据，`uchg` 锁定，禁止提交；
   - 被跟踪的 `application.properties` / `.env.example` 只能有占位符或 `${ENV:默认值}`。
4. **生产 profile 无可用默认密钥。** JWT、Companion 加密密钥、内部令牌缺失时生产应拒绝启动，不静默用开发默认值（缺口 BE-03）。
5. **鉴权以令牌为准。** 身份统一从 JWT 取，接口不得信任请求里自报的 `userId`；文件下载/预览、3D 资源变更、整聊已读等必须校验归属/成员/管理员（缺口 BE-01/BE-02/BE-04）。
6. **提交前自查：** `git grep -nE "授权码片段|真实密码片段" -- .` 应无匹配；`git status` 确认无 `uploads/`、`data/`、`nexus-chat-app/` 等误提交。

## 6. 命名与文案约定

- **命名通用、平实，不中二、不用科幻/玄学设定式命名。** 面向用户的界面文案尤其如此（例：待命屏用「暂无会话」，不用「计算机之眼 · 待命状态」这类表述）。
- 界面文案与术语面向正常软件用户，不做故弄玄虚的包装。
- 编码命名（类/变量/接口）与文案遵循同一原则，清晰可读优先。

---

## 7. 真实性与后端同步（防「假货」）

1. **界面显示的过程和数据必须来自模型与后端的真实返回，禁止用预设脚本、假数据、mock 结果冒充真实数据。**
2. 设计稿里没有后端功能支撑的元素**不做假**；设计稿没覆盖的部分，按当前主题自行设计，但数据必须真实。
3. **改界面必须同步核对后端。** 界面用到的接口、字段名、事件，必须与 Java / Python 后端的真实返回对上；必要时一并修后端。**光把界面改好看不算完成**，逻辑不对就是没完成。
4. **本机无可用 embedding 模型。** 涉及向量化（知识库上传、向量检索）的功能验证，不得依赖真实 embedding 调用；重点放在功能逻辑正确与页面设计，不做跑不通真模型为前提的「验证」。

## 8. 提交与协作（细节以 GIT-CHECKLIST 为准）

- **主线是 `feature-branch`**；`main` 是稳定兜底，只在 `feature-branch` 稳定后同步过去，不直接从 `main` 开发或合并；不 force push。
- 开短分支、本地三检查（前端 build / Agent pytest / Java mvn test）、PR base 固定 `feature-branch`、三项 CI 全绿才合并、merge commit 方式。
- **禁止 `git add -A` / `git add .`**；只 `git add` 具体目录/文件；清理分支只用 `-d`，禁止 `-D` 强删。
- **并行 worktree 警告**：当前有多个并行 worktree（`/Users/anglv/Nexus`、`bad-condor`、`partial-giraffe`、`slimy-silkworm` 等）。提交前 `git status` + 核对时间戳，确认改动归属本轮、且别的会话已收尾；不动别的 worktree 及其未提交修改。worktree 清单以 GIT-CHECKLIST §1 为唯一事实来源。
- 后端服务（Java 8080、Python 8100）由用户自己启停；改了 Python 代码后须提醒用户重启才生效。

## 9. 文档维护约定

1. **GAPS 是「代码与目标差距」的活清单**：修掉一条改状态为「已解决」并补提交号，**编号保持稳定不删**；新增缺口按前缀续号（`BE-`/`AG-`/`FE-`/`X-`/`OPS-`/`DOC-`）；每次更新重跑 `git rev-parse --short HEAD` 更新基线。
2. **README 分「现状」与「历史设计」两类**：现状以代码为准校对；未实现的能力一律标注，不宣称不存在的能力。
3. **改代码导致行为变化 → 同步改对应文档**，并回头核对 GAPS 里是否已有该缺口（已解决就标记，别让文档继续宣称「未解决」）。
4. **新增边界/红线 → 先来本文登记**，再落到具体文档。

## 10. 悬而未决（须产品/用户拍板）

以下问题代码无法回答，继续做下去方向会摇摆。实现前先拍板，拍板结果回写到本文或 ROADMAP：

1. 群公告/标签/共享文件/活跃度：补还是删？共享文件权限模型？
2. 联系人职位/部门/工号：要不要？来源（手动/组织架构导入）？
3. 忘记密码：是否允许邮箱验证码重置？重置后是否吊销所有设备会话？
4. 2FA：是否立即强制登录校验？
5. 拉黑语义：拉黑后历史消息保留吗？群聊里屏蔽吗？对方有提示吗？
6. Companion 合并节奏：立即迁移，还是先统一凭据、双轨保留到 M4 之后？
7. 冻结能力：帖子代码删除还是保留？通话入口是否立即隐藏？
8. Electron：是否需要托盘常驻/开机自启/自动更新？
9. 部署形态：Web 与 Electron 是否同指向一个生产域名？是否继续用 Cloudflare Tunnel？（2026-11-26 起，Web 的公网形态已定为 §11 所述；Electron 是否也指向它仍未定。）
10. 多端偏好：置顶/免打扰是否跨设备同步？
11. 消息删除：私聊「删除会话」是本地隐藏、双方清空，还是仅退出？

完整背景见 `GAPS.md` 第 8 节。

## 11. 公网环境边界（2026-11-26 登记）

2026-11-26 起，Web 前端发布在 Qoder 静态站点，后端经 Tailscale Funnel 对公网开放。公网后端是和本地开发环境完全分开的另一套：运行在 Mac 上的 Lima 虚拟机 `nexus-public` 里，独立的数据库、数据卷和密钥。日常操作、发布流程、扩展时的注意事项见 `docs/PUBLIC-OPERATIONS.md`；建设过程与每次核对的记录见 `docs/PUBLIC-ISOLATION-PLAN.md`。

以下各条要改，先由用户拍板、改本节，再动手：

1. **公网入口只有一条**：Funnel 的 443 → `127.0.0.1:18080`（虚拟机里的网关）。不把任何入口指向 8080、8100、3306、6379，不加第二条规则，不开 Tailscale SSH、子网路由、出口节点。Python Agent、MySQL、Redis、`/api/internal/**` 永不对公网开放（与 §2、§4.3 一致）。
2. **打开和关闭公网入口由用户亲手做。** 助手只核对，不执行 `tailscale funnel …`。
3. **两套环境不共用任何东西。** 公网环境不连本机的 MySQL / Redis，不导入本地数据，不挂载 Mac 的目录，不放用户自己的模型 Key；公网用户用自己的 Key 和服务商。
4. **不削弱隔离。** 容器保持非 root、只读根文件系统、无特权；虚拟机里的防火墙 `nexus-guard` 保持拦截去往 Mac、局域网、Tailscale 内网的连接。
5. **本地环境不受影响。** 加固功能一律做成开关，默认关闭，只在 `public` profile 打开，并有测试守住默认行为。不执行 `FunnelSecretPrep prepare`，不轮换 JWT 密钥。
6. **来源名单逐个列出，不用通配。** 来源检查不是身份验证，不能替代登录。
7. **后端不得新开不经校验的出站连接。** 凡是去连用户填写的地址，公网模式下必须拒绝本机、内网和 Tailscale 网段。
8. **邀请码由用户自己生成**，助手不代为生成、不回显。密钥同 §5.1。
9. **有真实账号后不清空公网数据**（`nexus-public.sh reset`），除非用户明确要求。会注册测试账号的验收脚本 `deploy/public/acceptance.py` 不在有真实账号的环境里跑。

§8 的“后端服务由用户自己启停”说的是本地的 Java 8080 和 Python 8100。公网环境的容器由助手用 `deploy/public/nexus-public.sh` 操作，用户也可以随时自己执行。
