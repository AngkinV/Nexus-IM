# Nexus 公网隔离加固计划（方案 B）

制定时间：2026-11-26 01:50（UTC+8）。基线：远端主线 `805f029`。状态（2026-11-26 06:30）：阶段 0、1、2、4 完成；阶段 3 和阶段 5 各有几步只能由你来做，见第 14 节。用户 2026-11-26 02:08 批准按本计划执行到底。

## 1. 目标

让陌生人可以通过 Qoder 网站使用 Nexus，同时做到两件事：

- 公网后端被攻破时，攻击者拿不到这台 Mac 上的文件，也连不到 Mac 和家里的内网。
- **公网环境和本地开发环境完全分开，任何一边坏了、停了、改了，另一边照常能用。**

## 3. 两套环境怎么分开

| | 本地环境（你日常用） | 公网环境（新建） |
|---|---|---|
| 运行位置 | Mac 上直接运行 | 一台独立 Linux 虚拟机里的 Docker 容器（见第 11 节） |
| 启动方式 | 和以前一样：`mvn spring-boot:run`、`ENGINE=langgraph .venv311/bin/python main.py`、`npm run dev` | 一条专用命令启动整套容器 |
| 主机端口 | 8080、8100、5173、3306、6379 | 只有 `127.0.0.1:18080` |
| 数据库和文件 | 现有 MySQL、Redis、`uploads`、`data` | 容器内独立的 MySQL、Redis 和数据卷 |
| 密钥 | 恢复为原来的开发配置 | 独立一套，存在钥匙串里，不落盘 |
| 代码版本 | 你工作区里的当前代码 | 从指定提交构建的镜像，不读工作区 |
| 加固开关 | 全部关闭，行为和今天一致 | 全部开启 |
| 谁启停 | 只由你启停 | 由我构建、启停和验证 |

六条隔离保证，每个阶段结束都要逐条验证：

1. **端口不重叠**：两套可以同时运行。
2. **数据不共享**：公网环境不连接本地的 MySQL 和 Redis，不挂载 Mac 上的任何目录。
3. **密钥不共享**：公网密钥泄露不影响本地，反过来也一样。
4. **代码不联动**：所有加固都有开关，默认关闭；本地不带公网配置启动时，行为与现在相同，并有测试守住。
5. **启停不联动**：停掉容器不影响本地，停掉本地后端不影响容器。
6. **可回退**：每个阶段一个独立 PR，可以单独撤回；公网出问题时关 Funnel、停容器即可，本地不受影响。

### 阶段 1：应用加固（改代码，全部默认关闭）

每一项单独一个 PR，三项 CI 通过后合入。每个 PR 都带两类测试：公网模式下生效，默认模式下行为不变。

**1A 公网模式与邀请码注册**
- 新增“公网模式”配置，只有容器环境启用。
- 邀请码：数据库只存哈希，带可用次数和有效期；注册时原子扣减。系统没有全局管理员角色，所以邀请码用容器内的命令行工具生成，不做管理界面。
- 公网模式下，发送邮箱验证码也必须先提供有效邀请码，防止别人用你的邮箱给任意地址发信。
- 新增一个只读接口返回“是否需要邀请码”；现有登录页的注册表单在需要时多显示一个邀请码输入框。不新增页面。

**1B 限流与登录锁定**
- 网关：按来源、按接口类型、全局三级限流；大请求体只允许上传接口。
- Java：同一账号登录连续失败后锁定一段时间；验证码按邮箱和全局设每日上限。

**1C 出站地址限制**
- 公网模式下，用户填写的模型地址和 MCP 地址一律不能解析到本机、内网、链路本地、Tailscale 网段和云元数据地址；不跟随重定向；连接时使用校验过的 IP，防止域名解析被中途替换。
- Java 现在只在工作台的模型供应商处校验；陪伴角色的模型地址和 MCP 地址登记处要补上。

**1D 配额**
- 每用户上传总量、单文件大小、全局上传总量。
- 每用户每日 AI 运行次数和并发数、MCP 服务数量上限。
- 具体数值做成配置，先用保守默认值（单文件 25MB、每用户 500MB、全局 5GB、每用户每天 200 次运行、并发 2）。

**1E 依赖升级**
- Spring Boot 3.2.0 升到 3.2.12；Python 依赖做一次漏洞扫描，只升级有问题的。

### 阶段 2：容器隔离

**2A 先做技术验证**（已完成，结果见第 11 节）
- 目标：容器内访问不到 Mac 本机、局域网和 Tailscale 网段，但能访问公网。

**2B 镜像与编排**
- 新建独立的编排文件，不修改仓库现有的 `docker-compose.yml`（那是服务器部署用的）。
- 容器以非 root 用户运行，根文件系统只读，去掉全部特权，限制 CPU、内存和进程数。
- 不挂载 Mac 目录，只用 Docker 数据卷。MySQL 和 Redis 不对主机开放端口，Redis 设密码。
- 对主机只开放 `127.0.0.1:18080`。
- 镜像从指定提交构建，不读你的工作区。

**2C 密钥与启动**
- 公网环境的密钥全部新生成，存在钥匙串的独立条目里（服务名 `nexus-public`）。启动脚本不把它们写到 Mac 的任何文件里，也不打印。虚拟机内 Docker 会把容器的环境变量（含这些密钥）保存在虚拟机磁盘上，这样虚拟机重启后服务能自己恢复。
- 公网环境不配置任何默认模型 Key。
- 邮箱验证码：公网环境默认不启用，注册只凭邀请码。这样容器里不用放任何邮箱密码，也不存在被人利用来发信的问题。以后提供专用邮箱后，改一项配置即可打开。（2026-11-26 02:10 按“不必询问、取最优解”定的。）
- 主机上直接对公网开放后端的方式停用：Funnel 只指向容器网关。

### 阶段 4：攻击清单验收（全部通过才开放）

在本机通过 `127.0.0.1:18080` 对容器环境逐项实测：

- 无邀请码不能注册，不能发验证码；邀请码用完即失效。

## 8. 防不住的部分

- Docker 或虚拟机自身的逃逸漏洞。概率低，靠保持更新。
- 防火墙在虚拟机内。攻击者如果先从容器逃逸、拿到了虚拟机的 root，就能撤掉它，然后连到 Mac 上的服务，包括只监听本机的 Redis 和代理。所以阶段 3 给本机 Redis 加密码仍然值得做。
- 容器被攻破时，容器里的公网用户数据会泄露。
- 后端访问用户填写的地址时，对方能看到你家的公网 IP。
- 流量攻击能让公网服务不可用，但碰不到电脑里的东西。
- 电脑关机、休眠或断网时，公网服务不可用。

## 11. 阶段 2 的运行环境：改用 Lima 虚拟机（2026-11-26 04:10 起）

### 为什么没用 Docker Desktop

Docker Desktop 启动时弹出了管理员密码提示，要配置它的特权组件。这一步只有你能做。我没有输入、也没有想办法绕过，关掉提示后它无法继续启动，我把它退出了，没有改它的任何设置。

之后改用不需要管理员权限的 Lima：

- 用 Homebrew 安装了 `lima` 2.3.0（安装包来自北外镜像，Homebrew 校验了哈希）。这是装在你电脑上的新软件。
- 先前试过 `brew install colima`，卡在下载上，什么都没装上。
- 撤掉这一切：`limactl delete -f nexus-public && brew uninstall lima`。
- 容器编排文件不依赖 Lima。你以后给 Docker Desktop 输一次密码，同一份编排也能在它上面跑，但防火墙那一层要另做。

### 虚拟机是什么样的

定义在 `deploy/public/lima.yaml`，名字 `nexus-public`。

- 系统是 Debian 13 官方云镜像，下载后对照了 Debian 官方的 SHA512。4 核、最多 4GB 内存、30GB 磁盘。
- 里面装的是 Debian 仓库的 Docker 26.1.5，每天自动装安全更新。
- 不共享任何 Mac 目录。
- 不继承 Mac 的代理设置。
- 只把虚拟机的 18080 端口转发到 Mac 的 `127.0.0.1:18080`，其他端口一律不转发。
- 防火墙先于 Docker 启动，Docker 依赖它：防火墙没起来，Docker 不会启动。

### 搭建时发现的三个问题

1. **Lima 默认把 Mac 的代理交给虚拟机。** 你的系统代理是本机 7890 端口，Lima 会把它改写成虚拟机能访问的地址写进虚拟机。本机代理能访问 Mac 能访问的一切，等于给防火墙开了后门。已关闭：虚拟机里没有任何代理设置。
2. **Lima 默认把虚拟机里的端口映射到 Mac 的本机地址。** 包括 UDP。已全部屏蔽，只留 18080。
3. **我自己的一次失误。** 我给虚拟机自身也加了“不许访问 Mac”的规则，把域名解析一起拦掉了，虚拟机启动卡了 6 分多钟。采样确认被拦的是解析服务后改正。

### 2A 验证结果

同一组探测跑两遍：先关掉防火墙作对照，再打开。从虚拟机自身和容器内各发起一次。

| 目标 | 防火墙关闭 | 防火墙开启 |
|---|---|---|
| Mac 本机 MySQL | 能连上 | 连不上 |
| Mac 本机 Redis（只监听本机） | 能连上 | 连不上 |
| Mac 本机代理 7890（只监听本机） | 能连上 | 连不上 |
| Mac 的局域网地址上的 MySQL | 能连上 | 连不上 |
| 虚拟机自身的 SSH（从容器发起） | 能连上 | 连不上 |
| 公网的两个地址和一个域名 | 能连上 | 能连上 |

- 关闭状态下的结果说明这些通路真实存在：不设防火墙时，虚拟机里的容器能连到 Mac 上只监听本机的服务。
- 给容器额外加上网络管理权限后再试，仍然连不上 Mac 的 Redis。
- Tailscale 网段（100.64.0.0/10）在拦截规则里，但测试时 Tailscale 是关的，没有活的目标做对照。阶段 5 打开 Tailscale 后要补测。
- 没有去探测局域网里的其他设备，只用了 Mac 自己的局域网地址。

### 带来的一个限制

公网环境的后端访问不到 Mac 上的代理，这是有意的。后果是：访客自己配置的模型服务商，必须能从你的网络直接访问。只有走代理才能访问的服务商，在公网环境里用不了。具体哪些服务商受影响我没有逐个测。

## 12. 公网环境怎么操作

都在 Mac 的终端里执行，路径相对仓库根目录。

| 要做的事 | 命令 |
|---|---|
| 看状态 | `bash deploy/public/nexus-public.sh status` |
| 启动（虚拟机没开时先开虚拟机） | `bash deploy/public/nexus-public.sh vm`，然后 `bash deploy/public/nexus-public.sh up` |
| 立刻停掉公网服务 | `bash deploy/public/nexus-public.sh down` |
| 发邀请码 | `bash deploy/public/nexus-public.sh invite create --uses 1 --days 7 --note 给谁的` |
| 看已发的邀请码 / 作废 | `... invite list`，`... invite revoke 编号` |
| 看最近 24 小时谁来过 | `bash deploy/public/nexus-public.sh summary` |
| 看某个服务的日志 | `bash deploy/public/nexus-public.sh logs backend 200` |
| 备份数据库到 `~/NexusPublicBackups` | `bash deploy/public/nexus-public.sh backup` |
| 每天自动备份并发一条摘要通知：开 / 关 / 看状态 | `bash deploy/public/nexus-public.sh schedule on`，`... schedule off`，`... schedule status` |
| 代码更新后重新构建并上线 | `bash deploy/public/nexus-public.sh build`，然后 `... up` |
| 整台虚拟机关掉 / 再打开 | `limactl stop nexus-public` / `bash deploy/public/nexus-public.sh vm` |
| 清空公网环境的全部数据（不可恢复） | `bash deploy/public/nexus-public.sh reset`，输入 RESET 确认，然后 `... up` |

要点：

- 邀请码只在生成时显示一次，数据库里只存哈希。
- `build` 用的是某个 git 提交（默认当前 HEAD），不读工作区里没提交的改动，也不会带上私有配置文件。
- 虚拟机重启后服务会自己起来，不需要再执行 `up`。Mac 重启后要执行一次 `vm`。
- 备份只含数据库，不含用户上传的文件。
- 访问日志每行只有时间、方法、路径、结果、访客地址。不记录查询参数、请求头和正文。
- 镜像来源：基础镜像按摘要固定，摘要取自 Docker Hub 官方。Python 依赖从腾讯云镜像下载，200 个包逐个对照了 pypi.org 的官方哈希，全部一致。

### 验收过程中发现并修复的问题

1. **Java 调用 Python 的 MCP 管理接口全部失败。** Java 发请求时带了升级到 HTTP/2 的协商头，Python 的 HTTP 解析器遇到它就不读请求体，签名校验因此失败。表现是：MCP 服务能保存，但测试连接永远是“未知”。已改为固定用 HTTP/1.1。这个缺陷和公网无关，本地环境同样有。
2. **用户自带的 MCP 服务一个都连不上。** 两层原因：安全模块只允许连管理员预先批准的地址，而这个名单默认是空的；握手时声明了一项“服务端可向用户提问”的能力，安全模块自己会拒绝这种握手。已加一个默认关闭的开关（任意来源，但只能是 https 且只能解析到公网地址），公网环境开启；握手不再声明那项能力。
3. **我第一版验收脚本把上面的失败误判成了通过。** 当时的判定是“没有连上就算通过”，而实际上是什么都连不上。加了公网对照项后才暴露出来。
4. **容器里域名解析每次要等 4 秒。** 配置的第一个 DNS 服务器从你的网络不应答（从 Mac 直接测也一样）。已换成实测有应答的。
5. **阿里云的 PyPI 镜像缺一个版本**，镜像构建失败，改用腾讯云镜像。

## 16. 每日备份与摘要（2026-11-26 08:55）

计划里阶段 5 写的是“每天出一份摘要”“定期备份”。之前只做了 `summary` 和 `backup` 两条手动命令，没有定时执行，这一节补上。

- `schedule on` 在你的账号下装一个 macOS 定时任务（`~/Library/LaunchAgents/cn.nexus.public.daily.plist`），每天 09:00 执行；电脑当时在睡眠，就等唤醒后补做。`schedule off` 卸掉它并删除这个文件。
- 每次执行：备份数据库，只保留最新的 14 份；然后弹一条系统通知，内容是过去 24 小时的请求数、登录失败数和注册数。完整摘要（含访客地址）追加在 `~/NexusPublicBackups/daily.log`，这个目录只有你的账号能读。
- 虚拟机关着时什么都不做，也不提示。虚拟机开着但备份失败时，弹一条“每日备份失败”的通知。
- 它不读钥匙串，也不联网，只在本机和虚拟机之间操作。

**现在是关闭的。** 公网还没开放，库是空的，每天弹一条“0 个请求”没有意义。你打开 Tailscale 后我在核对入口时一并启用。

实测过的：手动执行一次；旧备份超过 14 份时删掉最旧的、不碰目录里别的文件；虚拟机关闭时跳过；备份失败时报错退出；装上任务后由系统实际触发一次（退出码 0，日志和备份文件都生成了）；关闭后任务和文件都不在了。没有确认的：通知是否真的弹在你屏幕上——命令执行成功，但我看不到屏幕，勿扰模式下也可能不显示。试跑会弹出过两三条“Nexus 公网环境”的通知，是我测试产生的。

顺带修了 `backup` 的一个问题：数据库连不上时，它原来会直接退出并留下一个空的 `.part` 文件，没有任何提示。现在会删掉这个文件并报“备份不完整”。

容器日志的上限我也核对了：每个容器最多 3 个 10MB 的文件，不会把虚拟机磁盘写满。副作用是访问量很大时，`summary` 能回看的时间会短于 24 小时。
